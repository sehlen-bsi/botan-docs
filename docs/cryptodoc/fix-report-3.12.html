Behavior changed in 3.12.0

Since 3.12.0 the SHAKE_128/SHAKE_256 constructors reject a zero output length with Invalid_Argument (previously only lengths not divisible by 8 were rejected). The doc claimed 'arbitrary output lengths'.

Previous documentation text (src/01_hash.rst)

of the class.

implementation using a padding that is specific to SHAKE. In contrast to SHA-3
it allows variable output lengths which are provided to the constructor
of the class. The output length must be a non-zero multiple of eight
bits; since Botan 3.12.0 a zero output length is rejected with an

02_sym_enc.rst GCM: maximum message length now enforced

Behavior changed in 3.12.0 (GH #5521)

GHASH::update() now throws Invalid_State once the processed message exceeds (2^39 - 256)/8 bytes (the NIST SP 800-38D limit, i.e. 2^32 - 2 blocks). The doc claimed Botan does not check the plaintext length, and stated the limit as 2^32 - 1 blocks.

Previous documentation text (src/02_sym_enc.rst)

**Remark:** AES-GCM specification prescribes the maximum length of the
message to be encrypted to (2^32 - 1) blocks. Botan does not
check the plaintext length explicitly. It is currently up to the
application developer to choose correct data lengths.

New documentation text

**Remark:** The AES-GCM specification [GCM]_ prescribes a maximum
length of (2^39 - 256) bits, i.e. (2^32 - 2) blocks,
for the message to be encrypted. Since Botan 3.12.0 this limit is
enforced: the GHASH computation throws an ``Invalid_State`` exception
("GCM message length limit exceeded") once the processed plaintext or
ciphertext exceeds (2^39 - 256) / 8 bytes. The limit applies to
the message only, not to the associated data. In earlier versions Botan
did not check the plaintext length explicitly and it was up to the
application developer to choose correct data lengths.

02_sym_enc.rst CCM: message length limit corrected (off-by-one) and enforced early

Pre-existing off-by-one; early enforcement new in 3.12.0

The CCM limit is 2^(8L) - 1 bytes, not 2^(8L) (pre-existing doc error). Since 3.12.0 an over-long message is rejected with Invalid_State already while being buffered in process(), instead of only at finish() time.

Previous documentation text (src/02_sym_enc.rst)

**Remark:** In Botan the default maximum length of the message is
2^24 bytes (with a nonce size of 12 byte).
The maximum length can be configured to be 2^(8*L) by initializing L with a value between 2 and 8.
Note that this parameter is denoted q in [CCM]_.
The size of the nonce is then (15-L) bytes.

New documentation text

**Remark:** In Botan the default maximum length of the message is
2^24 - 1 bytes (with a nonce size of 12 byte).
The maximum length can be configured to be 2^(8*L) - 1 by initializing L with a value between 2 and 8.
Note that this parameter is denoted q in [CCM]_.
The size of the nonce is then (15-L) bytes. Since Botan 3.12.0, a
message exceeding this limit is already rejected with an
``Invalid_State`` exception while it is buffered in ``process()``;
previously the overflow was only detected when the length was encoded
during ``finish()``.

05_01_dh.rst DH check_key(): condition list rewritten for 3.12.0

Behavior changed in 3.12.0 (commit 3d7119818)

DH_PrivateKey::check_key() now delegates to DL_PrivateKey::check_key() = verify_group() && verify_private_element(x). The public-value conditions are no longer part of the private-key check; x > q (if q is set) is now rejected; and y = g^x mod p is not verified by either check. The Miller-Rabin description was also corrected (error probability 2^-128, 65 iterations for external groups).

Previous documentation text (src/05_01_dh.rst)

      Optionally the generated parameters and the DL_Group parameters can
      be verified with a call to ``check_key(RandomNumberGenerator& rng,
      bool strong)``. The generated values and the used discrete logarithm
      group ``fail`` the check if one of the following conditions is met.

      -  y < 2
      -  y >= p
      -  x < 2
      -  x >= p
      -  g < 2
      -  p < 3
      -  q < 0
      -  q != 0 and (p - 1) mod q != 0
      -  q != 0 and g^q mod p != 1
      -  Miller-Rabin primality test for ``p`` or ``q`` fails with 6 (65 if
         ``strong`` is true) test iterations. The test is performed with the
         function ``is_prime()`` for non random numbers.
      -  Lucas primality test of ``p`` or ``q`` fails.
      -  y != g^x mod p

New documentation text

      Optionally the generated parameters and the DL_Group parameters can
      be verified with a call to ``check_key(RandomNumberGenerator& rng,
      bool strong)``. Since Botan 3.12.0, ``DH_PrivateKey::check_key()``
      verifies the group (see below) and the private value ``x``
      (``DL_Group::verify_private_element()``); it fails if one of the
      following conditions is met:

      -  x <= 1
      -  x >= p
      -  q > 0  and  x > q

      ``DH_PublicKey::check_key()`` verifies the group and the public
      value ``y`` (``DL_Group::verify_public_element()``); it fails if
      one of the following conditions is met:

      -  y <= 1
      -  y >= p
      -  q != 0  and  g^q mod p != 1

      Note that neither check verifies the consistency of the key pair,
      i.e. y = g^x mod p is not checked.

      The group verification (``DL_Group::verify_group()``) is skipped
      for Botan's builtin named groups unless ``strong`` is set. It fails
      if one of the following conditions is met:

      -  g < 2
      -  p < 3
      -  q < 0
      -  q != 0  and  (p - 1) mod q != 0
      -  q != 0  and  g^q mod p != 1
      -  Miller-Rabin primality test of ``p`` or ``q`` (if ``q`` is set)
         fails. The test is performed with the function ``is_prime()``
         with an error probability of 2^-128, resulting in 65
         test iterations for groups obtained from an external source and
         a reduced, bit-size-dependent iteration count for randomly
         generated groups.
      -  Lucas primality test of ``p`` or ``q`` fails.
      -  q = 0 and the group stems from an external source and
         g^i mod p = 1 for some 2 <= i < 100
         (2 <= i < 1000 if ``strong`` is set), i.e. the group
         order is very small.
