X.509 Certificates
==================

Botan X.509 certificate tests validate X.509 format processing and
correct certificate path validation. The tests are divided into four
independent test suites:

-  X.509 unit tests (in :srcref:`src/tests/unit_x509.cpp`) performs tests with
   dynamically generated valid and invalid X.509 certificates, validates
   processing of certificate extensions or expired certificates.
-  X.509 tests (in :srcref:`src/tests/test_x509_path.cpp`) performs extended
   certificate path validation tests with valid and invalid
   certificates.
-  Extended X.509 name constraints tests (in
   :srcref:`src/tests/test_name_constraint.cpp`) performs an extended test
   with different named constraints used in CA certificates.
-  OCSP tests (in :srcref:`src/tests/test_ocsp.cpp`) perform tests for parsing
   OCSP requests and responses, validating responses and testing online
   OCSP checks.


**Remark from review of 3.12.0:** Botan 3.12.0 reworked large parts of the
X.509 code (strict DER decoding of PKIX types, incremental DFS path building,
IPv6 name constraints, optimized certificate and CRL indexing). Accordingly,
all four test files received additions, which are described in the respective
sections below. Furthermore, the expected results of some existing test
vectors changed: in `src/tests/data/x509/bsi/expected.txt` the expected error
messages of the test cases ``ext_05`` and ``ext_10`` were adapted to the
stricter DER decoding, and in `src/tests/data/x509/nist/expected.txt` the
expected result of ``test76`` changed from ``Verified`` to ``Certificate is
revoked``, since the CRL IssuingDistributionPoint extension (marked critical,
with the unhandled ``onlyContainsCACerts`` field) is now treated as
unprocessable so that affected certificates are assumed revoked.

In the following, we describe these tests in more detail.

X.509 Unit Test
---------------

X.509 unit test performs tests with dynamically generated valid and
invalid X.509 certificates and validates their processing in Botan. The
test validates key usage extension, expiration dates, or processing of
self-signed certificates and certificate issuer properties.

The test is implemented in :srcref:`src/tests/unit_x509.cpp`.


The following X.509 certificate tests are executed:

-  Validity period: tests with valid and expired certificates
-  Issuer information storage: tests storage and access to issuer data
   in certificates
-  Certificate revocation
-  Detection of self-signed certificates
-  Key usage constraints for different cryptographic algorithms: DH,
   ECDH, RSA, ElGamal, DSA, ECDSA, ECGDSA, ECKCDSA
-  X.509v3 extension handling, including writing and reading custom
   X.509v3 extensions

**Remark from review of 3.12.0:** The following tests were added in
`unit_x509.cpp`:

-  A negative test that decoding an extension block containing two extensions
   with the same OID is rejected with a ``Decoding_Error``
-  A test that the distributionPoint URI of a CRL's
   IssuingDistributionPoint extension is decoded correctly
-  A test that a CRL entry whose serial number is encoded as a negative
   two's-complement INTEGER is decoded to its magnitude, so that it matches
   the serial number of the corresponding certificate during revocation
   checking

X.509 Test with Certificate Files
---------------------------------

Botan X.509 certificate validation is tested with a set of valid and
invalid certificates. Sets of test vectors coming from same origin are
placed in same folder:

-

   -  Test vectors generated with the tool x509test [x509test] reside in
      :srcref:`src/tests/data/x509/x509test`
   -  NIST test vectors are in :srcref:`src/tests/data/x509/nist`
   -  X.509 extended path validation test vectors are in
      :srcref:`src/tests/data/x509/extended`
   -  Test vectors generated on behalf of BSI are in
      :srcref:`src/tests/data/x509/bsi`

Test vectors from each origin are handled by a separate class. All these
test classes are implemented in :srcref:`src/tests/test_x509_path.cpp`. The
following certificate properties and certificates are tested with the
generated certificates:

-  Key usage and CA key usage extension

-  CA flag availability

-  CA certificates constructed to contain a loop during validation

-  Self-signed certificates

-  Subject name

-  Alternative names

-  Name constraints with DNS names

-  Wildcard certificates

-  Validity period

-  Path validation:

   -  Positive tests of certificate verification

      -  at least one valid path is found

   -  Negative tests invalidating path if:

      -  insecure hash algorithm has been used in the production of an
         intermediate or a target certificate's signature
      -  one of CAs uses week keys for signing of certificates
      -  no trust anchor found for built path
      -  validity period requirements of one of the certificates in path
         are not met
      -  revocation information for a certificate in path is not
         available or CRL is invalid
      -  target or intermediate CA certificate is revoked
      -  signature of a target or intermediate CA certificate is wrong
      -  unknown critical extension is encountered
      -  CA certificate requirements defined by a standard are not met
         by an intermediate CA

The tests are implemented in :srcref:`src/tests/test_x509_path.cpp`. The

**Remark from review of 3.12.0:** Two tests were added in
`test_x509_path.cpp`:

-  A path building test (test name ``x509_path_building``): Botan 3.12.0
   reworked the depth-first-search certificate path building to work
   incrementally. The test uses a dedicated certificate set in
   :srcref:`src/tests/data/x509/path_building` consisting of a root
   certificate, two levels of seven intermediate certificates each, and seven
   end-entity certificates. Each end-entity certificate is validated at a
   fixed validation time with all intermediate certificates supplied in an
   unspecified order, and the validation result is compared to the expected
   result (``Verified`` for all seven chains) from the accompanying
   ``expected.txt``. This ensures that the path builder finds a valid path
   through the ambiguous intermediate certificates.
-  A regression test (test name ``x509_cve_2026_35580``) for CVE-2026-35580:
   an end-entity certificate from
   `src/tests/data/x509/cve_2026_35580` is validated against the
   accompanying root certificate at a fixed validation time, and the test
   asserts that path validation fails with ``Cannot establish trust``.

Extended X.509 Name Constraints Test
------------------------------------

The name constraints extension is an extension used in CA certificates.
It indicates a name space within which all subject names of the issued
certificates must be located. For example, it indicates the IP addresses
of the issued certificates or their domain names.

This test extends the previous tests with further further name
constraints:

-  Domain names
-  DNS name
-  email address
-  IP address

The following tables show example test cases with one valid and one
invalid test vector. All test vectors are included as certificates in
:srcref:`src/tests/data/x509/name_constraint`.

**Remark from review of 3.12.0:** Botan 3.12.0 added support for IPv6 name
constraints in certificate path validation (GH #5534, #5537). Accordingly,
`test_name_constraint.cpp` received three new tests, which are described at
the end of this section: a chain validation test for IPv6 name constraints, a
test vector based test for the DER validation of ``GeneralName`` iPAddress
encodings, and a test for a leaf certificate with an empty subject DN whose
subject alternative name is matched against a directoryName constraint. The
test vectors referenced above did not change.

The following tests were added in the review cycle for Botan 3.12.0:

-  **IPv6 name constraint chains** (test name
   ``x509_name_constraint_ipv6_chains``): validates certificate chains
   against IPv6 (and mixed IPv4/IPv6) name constraints. The certificates
   reside in :srcref:`src/tests/data/x509/name_constraint_ipv6` and cover the
   following scenarios, each with a leaf certificate that is expected to pass
   and leaf certificates that are expected to fail with "Certificate does not
   pass name constraint":

   -  an IPv6 permittedSubtree (``2001:db8::/32``) with a subject
      alternative name inside respectively outside the subtree
   -  an IPv6 excludedSubtree with a subject alternative name outside
      respectively inside the subtree
   -  a root certificate permitting only an IPv4 range (``10.0.0.0/8``),
      which must reject a leaf with an IPv6 subject alternative name (and
      vice versa for a root permitting only an IPv6 range), since iPAddress
      constraints of one address family constrain the entire iPAddress name
      form (RFC 5280, section 4.2.1.10)
   -  constraints across multiple issuers: the root permits
      ``{10.0.0.0/8, 2001:db8::/32}``, the intermediate narrows the
      permitted subtrees and adds excluded subtrees; leaves with one IPv4
      and one IPv6 subject alternative name each violate the permitted or
      excluded subtrees of the root or the intermediate in all combinations
   -  IPv4-mapped IPv6 subject alternative names tested against IPv4
      excluded and permitted subtrees (a mapped address inside an excluded
      IPv4 range is rejected; a mapped address inside a permitted IPv4-only
      range is also rejected, as RFC 5280 gives no clear guidance on
      matching mapped addresses across address families)

-  **GeneralName iPAddress mask validation** (test name
   ``x509_name_constraint_ip_mask``): a test vector based test using
   :srcref:`src/tests/data/x509/general_name_ip.vec`. Each vector consists
   of an address and a netmask, which are DER-encoded as a ``GeneralName``
   iPAddress ([7] IMPLICIT OCTET STRING) and then decoded with strict DER
   limits. Valid vectors (IPv4 and IPv6 addresses with contiguous netmasks)
   must be accepted; invalid vectors (e.g. non-contiguous netmasks or
   invalid lengths) must be rejected with a ``Decoding_Error``.

-  **Empty subject DN with SAN directoryName** (test name
   ``x509_name_constraint_empty_subject``): validates a chain from
   :srcref:`src/tests/data/x509/name_constraint_empty_subject` in which the
   intermediate CA carries a critical name constraints extension with a
   directoryName permittedSubtree and the leaf certificate has an empty
   subject DN and a critical subject alternative name extension containing a
   directoryName inside the permitted subtree. Path validation must succeed.

OCSP Tests
----------

Botan's OCSP code is tested using different tests that parse OCSP
requests and OCSP responses, validate OCSP responses (in terms of
signature validation) and also using online tests for randombit.net.
Online tests are only executed if BOTAN_HAS_ONLINE_REVOCATION_CHECKS is
set. The tests are implemented in :srcref:`src/tests/test_ocsp.cpp`. All
test data can be found in :srcref:`src/tests/data/x509/ocsp`.

**Remark from review of 3.12.0:** The following tests were added in
`test_ocsp.cpp`:

-  A test parsing an OCSP response (generated with ``openssl ocsp ...
   -resp_key_id``) that identifies the responder via the byKey ResponderID
   choice instead of a name: the parsed response must report an empty signer
   name, the signer key hash must equal the SHA-1 hash of the responder
   certificate's public key, and the responder certificate must be found via
   the key hash.
-  A test that partial OCSP stapling preserves the per-slot gap for the
   online fallback: ``PKIX::check_ocsp`` is invoked on a three-certificate
   chain with a stapled response for only the intermediate (respectively only
   the end-entity) certificate, and the test verifies that the returned
   status list keeps an empty entry exactly at the position of the
   certificate without a stapled response.

Limbo X.509 Tests
-----------------

Limbo [#limbo_url]_ is a testsuite for evaluating X.509 path validation
implementations that is maintained by "Trail of Bits". It contains several
thousand certificate validation test cases.

Botan's CI is running the entire Limbo test harness via the library's python
binding to verify proper path building and validation. Less than 1% of the
tests are either ignored, disabled or produce a different result than expected.
See :srcref:`src/scripts/run_limbo_tests.py`
for the full details of the irregular test results.

.. [#limbo_url] Limbo X.509 test suite: https://x509-limbo.com/
