X.509 Certificates
==================

Botan X.509 certificate tests validate X.509 format processing and
correct certificate path validation. The tests are divided into the
following independent test suites:

-  X.509 unit tests (in :srcref:`src/tests/unit_x509.cpp`) performs tests with
   dynamically generated valid and invalid X.509 certificates, validates
   processing of certificate extensions or expired certificates.
-  X.509 tests (in :srcref:`src/tests/test_x509_path.cpp`) performs extended
   certificate path validation tests with valid and invalid
   certificates.
-  Extended X.509 name constraints tests (in
   :srcref:`src/tests/test_name_constraint.cpp`) performs an extended test
   with different named constraints used in CA certificates.
-  OCSP tests (in :srcref:`src/tests/test_ocsp.cpp`) perform tests for parsing
   OCSP requests and responses, validating responses and testing online
   OCSP checks.
-  X.509 distinguished name tests (in :srcref:`src/tests/test_x509_dn.cpp`)
   test the parsing, encoding, formatting and comparison of X.509
   distinguished names.
-  CRL distribution point and authority information access tests (in
   :srcref:`src/tests/test_x509_cdp_aia.cpp`) test the decoding, encoding
   and revocation checking semantics of the CRLDistributionPoints,
   IssuingDistributionPoint and AuthorityInformationAccess extensions.


Botan 3.12.0 reworked large parts of the X.509 code (strict DER decoding
of PKIX types, incremental depth-first-search path building, IPv6 name
constraints, and optimized certificate and CRL indexing). Botan 3.13.0
continued this rework (canonical decoding and comparison of distinguished
names addressing CVE-2026-48057, a corpus-based rewrite of the name
constraint tests, CRL scope and distribution point matching per RFC 5280,
section 6.3.3, support for the noRevAvail extension of RFC 9608,
enforcement of the context in which an extension may appear,
sign-preserving handling of serial numbers, and a hardened OCSP
implementation). The tests added for these changes are described in the
respective sections below.

In the following, we describe these tests in more detail.

X.509 Unit Test
---------------

X.509 unit test performs tests with dynamically generated valid and
invalid X.509 certificates and validates their processing in Botan. The
test validates key usage extension, expiration dates, or processing of
self-signed certificates and certificate issuer properties.

The test is implemented in :srcref:`src/tests/unit_x509.cpp`.


The following X.509 certificate tests are executed:

-  Validity period: tests with valid and expired certificates
-  Issuer information storage: tests storage and access to issuer data
   in certificates
-  Certificate revocation
-  Detection of self-signed certificates
-  Key usage constraints for different cryptographic algorithms: DH,
   ECDH, RSA, ElGamal, DSA, ECDSA, ECGDSA, ECKCDSA
-  X.509v3 extension handling, including writing and reading custom
   X.509v3 extensions
-  Rejection of an extension block that contains two extensions with the
   same OID with a ``Decoding_Error``
-  Decoding of the distributionPoint URI of a CRL's
   IssuingDistributionPoint extension
-  Decoding of a CRL entry whose serial number is encoded as a negative
   two's-complement INTEGER

The last three tests were added in Botan 3.12.0.

Since Botan 3.13.0, certificate and CRL entry serial numbers are
represented by the sign-preserving ``X509_Serial_Number`` type, and the
following tests were added:

-  Encoding and decoding of the ``X509_Serial_Number`` type: golden DER
   encodings of positive, negative and zero serial numbers,
   normalization of redundant encodings, numeric ordering, the RFC 5280
   conformance predicate (positive value of at most 20 octets), and
   generation of random serial numbers
-  Decoding of certificates with positive, negative, zero, 20-octet and
   21-octet serial numbers from
   :srcref:`src/tests/data/x509/serial_numbers`
-  CRL revocation matching respects the sign of the serial number: a
   revoked certificate with serial number -255 does not cause revocation
   of a certificate with serial number 255 (and vice versa), and the
   sign survives re-encoding of the CRL
-  Derivation of the subject key identifier as the SHA-1 hash of the
   subjectPublicKey (RFC 5280, section 4.2.1.2, method 1), checked
   against externally generated RSA and ECDSA certificates
-  Rejection of extensions appearing in the wrong context, using the
   files in :srcref:`src/tests/data/x509/wrong_context_ext`: certificates
   containing CRL-only extensions (CRLNumber, ReasonCode or
   IssuingDistributionPoint) are rejected with a ``Decoding_Error``,
   CRLs and CRL entries containing a SubjectAlternativeName are rejected
   with a ``Decoding_Error``, and CRLs with an unknown critical CRL or
   CRL entry extension are treated as unusable during revocation
   checking
-  Decoding of CRL numbers that exceed the machine word size (a CRL with
   a 160-bit CRLNumber extension)
-  Decoding of LDAP URIs with an empty authority component from the
   AuthorityInformationAccess and CRLDistributionPoints extensions of
   externally generated certificates

X.509 Test with Certificate Files
---------------------------------

Botan X.509 certificate validation is tested with a set of valid and
invalid certificates. Sets of test vectors coming from same origin are
placed in same folder:

-

   -  Test vectors generated with the tool x509test [x509test] reside in
      :srcref:`src/tests/data/x509/x509test`
   -  NIST test vectors are in :srcref:`src/tests/data/x509/nist`
   -  X.509 extended path validation test vectors are in
      :srcref:`src/tests/data/x509/extended`
   -  Test vectors generated on behalf of BSI are in
      :srcref:`src/tests/data/x509/bsi`

Test vectors from each origin are handled by a separate class. All these
test classes are implemented in :srcref:`src/tests/test_x509_path.cpp`. The
following certificate properties and certificates are tested with the
generated certificates:

-  Key usage and CA key usage extension

-  CA flag availability

-  CA certificates constructed to contain a loop during validation

-  Self-signed certificates

-  Subject name

-  Alternative names

-  Name constraints with DNS names

-  Wildcard certificates

-  Validity period

-  Path validation:

   -  Positive tests of certificate verification

      -  at least one valid path is found

   -  Negative tests invalidating path if:

      -  insecure hash algorithm has been used in the production of an
         intermediate or a target certificate's signature
      -  one of CAs uses week keys for signing of certificates
      -  no trust anchor found for built path
      -  validity period requirements of one of the certificates in path
         are not met
      -  revocation information for a certificate in path is not
         available or CRL is invalid
      -  target or intermediate CA certificate is revoked
      -  signature of a target or intermediate CA certificate is wrong
      -  unknown critical extension is encountered
      -  CA certificate requirements defined by a standard are not met
         by an intermediate CA


Botan 3.13.0 reworked the CRL processing (scope matching of the
IssuingDistributionPoint extension according to RFC 5280, section 6.3.3,
and a dedicated status code for CRLs carrying an unprocessable critical
extension) and tightened the decoding of subject alternative names. The
expected results of several test cases were adapted accordingly:

-  CRLs with an unprocessable critical extension (e.g. a delta CRL
   indicator) now yield ``CRL contains a critical extension that could
   not be processed`` instead of treating the affected certificates as
   revoked (BSI test cases ``CRL_06`` and ``CRL_11``; NIST test cases
   ``test68`` to ``test71`` and ``test75``)
-  CRLs that are out of scope for the certificate in question now yield
   ``No revocation data`` (BSI test cases ``CRL_13`` and ``CRL_15``;
   NIST test case ``test76``, whose CRL carries an
   IssuingDistributionPoint extension with ``onlyContainsCACerts`` and
   therefore cannot be used to determine the revocation status of an
   end-entity certificate)
-  x509test certificates whose subject alternative name contains a
   dNSName with a wildcard outside of the leftmost label (e.g.
   ``*.*.*`` or ``www.*.test``) are now rejected during decoding, so
   the respective test cases yield ``Certificate extension encoding
   error``

Extended X.509 Name Constraints Test
------------------------------------

The name constraints extension is an extension used in CA certificates.
It indicates a name space within which all subject names of the issued
certificates must be located. For example, it indicates the IP addresses
of the issued certificates or their domain names.

In Botan 3.13.0 the name constraint tests in
:srcref:`src/tests/test_name_constraint.cpp` were rewritten as a
corpus-driven test suite (in part motivated by CVE-2026-48057, a bypass
of the enforcement of directoryName constraints): each test case is a
single PEM file in :srcref:`src/tests/data/x509/name_constraints` that
contains the certificate chain in leaf-first order, all chains share the
trust anchor ``root.pem``, and the file ``expected.txt`` maps each test
case to the expected path validation result. The corpus contains almost
300 chains covering the following name forms and scenarios:

-  DNS names (case insensitivity, wildcard subject alternative names,
   fallback to the common name if no subject alternative name is
   present, embedded NUL bytes, and malformed constraints such as
   trailing dots, underscores or wildcards)
-  email addresses (rfc822Name constraints in host, subtree and mailbox
   form, SmtpUTF8Mailbox subject alternative names, and PKCS#9 email
   address DN attributes)
-  URIs (constraints matched against the host part of URI subject
   alternative names, including IP-literal hosts)
-  IP addresses (IPv4 and IPv6 permitted and excluded subtrees,
   mixed-family chains, IPv4-mapped IPv6 addresses, and malformed
   encodings such as non-contiguous netmasks or wrong lengths)
-  directoryNames (multi-AVA RDNs, RDN ordering, string type,
   case and whitespace folding according to RFC 5280, and empty subject
   DNs with directoryName subject alternative names)
-  constraint composition across multiple CAs (narrowing of permitted
   subtrees, union of excluded subtrees, empty intersections),
   self-issued certificates, and malformed GeneralName and
   GeneralSubtree encodings

(using the certificates in

-  ``x509_name_constraint_factory_validation``: strict validation at the

OCSP Tests
----------

Botan's OCSP code is tested using different tests that parse OCSP
requests and OCSP responses (among others, responses for randombit.net),
validate OCSP responses (in terms of signature validation) and also
using an online test that checks the revocation status of a DigiCert
intermediate CA certificate. Online tests are only executed if
BOTAN_HAS_ONLINE_REVOCATION_CHECKS is set. The tests are implemented in
:srcref:`src/tests/test_ocsp.cpp`. All test data can be found in
:srcref:`src/tests/data/x509/ocsp`.

The parsing tests also cover an OCSP response (generated with
``openssl ocsp ... -resp_key_id``) that identifies the responder via the
byKey ResponderID choice instead of a name: the parsed response must report
an empty signer name, the signer key hash must equal the SHA-1 hash of the
responder certificate's public key, and the responder certificate must be
found via the key hash.

Furthermore, it is tested that partial OCSP stapling preserves the per-slot
gap for the online fallback: ``PKIX::check_ocsp`` is invoked on a
three-certificate chain with a stapled response for only the intermediate
(respectively only the end-entity) certificate, and it is verified that the
returned status list keeps an empty entry exactly at the position of the
certificate without a stapled response.

Both tests were added in Botan 3.12.0.

Botan 3.13.0 hardened the OCSP implementation. The following tests were
added in :srcref:`src/tests/test_ocsp.cpp`:

-  OCSP ``CertID`` matching respects the sign of the certificate serial
   number: a ``CertID`` built from a negative serial number does not
   match the certificate with the positive serial number of the same
   magnitude (and vice versa), also after an encode/decode round trip.
-  Stricter parsing of the outer ``OCSPResponse`` structure: a response
   with a non-successful status that nevertheless contains
   responseBytes is rejected, a successful status without responseBytes
   is rejected (RFC 6960, section 4.2.1), an unknown OCSPResponseStatus
   value is rejected, and a bare non-successful status (e.g. tryLater)
   still parses.
-  Decoding of an OCSP response with a revoked certificate status,
   including the revocation time and the thisUpdate/nextUpdate fields.
-  Encoding and decoding of ``SingleResponse`` structures with good,
   unknown and revoked certificate status against golden encodings
   (produced with OpenSSL), including the handling of the optional
   revocation reason. The dates in a ``SingleResponse`` must be encoded
   as GeneralizedTime; UTCTime values are rejected both when encoding
   and when decoding.

Furthermore, the OCSP-based path validation tests in
:srcref:`src/tests/test_x509_path.cpp` were extended for the hardened
revocation policy of Botan 3.13.0:

-  The maximum accepted age of an OCSP response without a nextUpdate
   field is now limited by default: under the default validation
   restrictions (``max_ocsp_age`` of 7 days) such a response that is
   older than the limit leads to the status ``OCSP_IS_TOO_OLD``, while
   a ``max_ocsp_age`` of zero disables the age check.
-  OCSP soft-fail conditions (e.g. the OCSP server was not available or
   no revocation URL is known) no longer satisfy a required revocation
   check by default: they lead to ``NO_REVOCATION_DATA`` unless the new
   ``accept_ocsp_softfail`` restriction is set, in which case the
   validation succeeds but retains the soft-fail status as a warning.
   A stapled non-successful OCSP response (e.g. tryLater) is not a
   soft-fail condition, and a successful CRL check satisfies the
   revocation requirement even if the OCSP check soft-failed.

X.509 Distinguished Name Tests
------------------------------

Botan's handling of X.509 distinguished names (DNs) is tested in
:srcref:`src/tests/test_x509_dn.cpp`. The test ``x509_dn_cmp`` compares
pairs of DER-encoded DNs from :srcref:`src/tests/data/x509_dn.vec` and
checks that the equality and ordering operators yield the expected
result.

Botan 3.13.0 reworked the decoding and comparison of DNs: the RDN
grouping (i.e. multiple attribute-value pairs within one RDN SET) is
preserved when decoding, and the comparison folds case, whitespace and
equivalent string types as required by RFC 5280. This rework addresses
the name constraint enforcement bypass CVE-2026-48057. The following
tests were added:

-  ``x509_dn_valid``: parses each DN string from
   :srcref:`src/tests/data/x509/x509_dn_valid.vec`, compares the DER
   encoding of the parsed DN with the expected bytes, decodes the DER
   encoding back to an equal DN, and checks the string formatting.
-  ``x509_dn_invalid``: checks that the malformed DN strings from
   :srcref:`src/tests/data/x509/x509_dn_invalid.vec` are rejected.
-  ``x509_dn_string``: round trips DNs with single- and multi-AVA RDNs
   through the string form (``,`` separates RDNs, ``+`` separates the
   attribute-value pairs of one RDN), checks the escaping of control
   characters and embedded NUL bytes in attribute values, and checks
   that a failed decoding leaves the DN object unchanged.
-  ``x509_dn_ordering``: checks pairs of DNs from
   :srcref:`src/tests/data/x509/x509_dn_ordering.vec` for the expected
   equality and verifies that the less-than operator forms a strict
   weak ordering (asymmetry, transitivity and consistency with
   ``std::set``) over all DNs in the file.

CRL Distribution Point and Authority Information Access Tests
-------------------------------------------------------------

Botan 3.13.0 reworked the handling of the CRLDistributionPoints (CDP)
and IssuingDistributionPoint (IDP) extensions during revocation
checking as well as the handling of the AuthorityInformationAccess
(AIA) extension. The test ``x509_cdp_aia``, added in Botan 3.13.0 in
:srcref:`src/tests/test_x509_cdp_aia.cpp`, covers these changes; the
certificates and CRLs used are located in
:srcref:`src/tests/data/x509/cdp_aia`. The following aspects are tested:

-  Decoding of IDP extensions with the ``onlyContainsUserCerts``,
   ``onlyContainsCACerts``, ``onlySomeReasons`` and ``indirectCRL``
   fields as well as multi-field IDPs; decoding of certificate CDP
   extensions with multiple URIs, multiple distribution points,
   directoryName partitions and cRLIssuer fields
-  CRL applicability during path validation according to RFC 5280,
   section 6.3.3: a CRL with ``onlyContainsUserCerts`` is consulted for
   an end-entity certificate, a CRL with ``onlyContainsCACerts`` is
   not; a reason-limited CRL (``onlySomeReasons`` in the IDP or a
   reasons field in the certificate's distribution point) provides only
   partial coverage and does not satisfy a required revocation check,
   but still proves a positive revocation if the certificate is listed;
   an indirect CRL is rejected as inapplicable; the distribution point
   names of the CRL and the certificate are matched against each other,
   with the certificate issuer DN acting as the implicit distribution
   point if the certificate has no CDP extension
-  Strictness of the encoders and decoders: empty IDPs, IDPs with
   multiple scope booleans, malformed fullName or directoryName fields,
   cRLIssuer fields that are not a single directoryName, out-of-order
   or duplicated DistributionPoint fields, malformed ReasonFlags BIT
   STRING values and the (unsupported) nameRelativeToCRLIssuer choice
   are rejected
-  Construction and mutation of AIA extensions via AccessDescription
   entries, preservation of access methods other than OCSP and CA
   issuers (e.g. id-ad-stirTNList) and of directoryName access
   locations, and rejection of malformed or empty accessLocations

Limbo X.509 Tests
-----------------

Limbo [#limbo_url]_ is a testsuite for evaluating X.509 path validation
implementations that is maintained by "Trail of Bits". It contains several
thousand certificate validation test cases.

Botan's CI is running the entire Limbo test harness via the library's python
binding to verify proper path building and validation. Less than 1% of the
tests are either ignored, disabled or produce a different result than expected.
See :srcref:`src/scripts/run_limbo_tests.py`
for the full details of the irregular test results.

.. [#limbo_url] Limbo X.509 test suite: https://x509-limbo.com/
